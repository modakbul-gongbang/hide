# PRD: Workspace 제어 CLI

## Goal

Herdr pane에서 일하는 에이전트가 사용자의 요청에 따라 자기 Workspace의 파일·브라우저·diff를 열고 Views를 정리할 수 있게 한다.
로컬과 SSH 원격 pane에서 같은 명령을 사용하며, 사용자가 다른 화면에서 하던 작업과 입력을 유지하고 현재 환경에서 가능한 기능을 컨텍스트로 안내한다.

## Non-goals

- 다른 Workspace 지정·제어는 제공하지 않는다. 여러 Workspace를 관리하려면 별도 사용자 요청으로 범위를 다시 정한다.
- 터미널 pane·tab 생성, 명령 실행, Workspace 생성·관리는 이 CLI에 추가하지 않는다. 기존 도구를 계속 사용하며 별도 요청 시 재검토한다.
- 파일 내용 편집·저장·폐기나 Git 변경 작업은 추가하지 않는다. 미저장 변경은 기존 편집 UI에서 처리하며 별도 편집 CLI 요청 시 재검토한다.
- Swift 신규 기능과 일반 웹의 내장 브라우저 페이지 렌더링은 제외한다. 전체 기능은 Electron에서 사용하며 지원 대상 확대 요청 시 재검토한다.
- 앱 자동 실행 및 운영 중인 Mac·원격 호스트의 설치·교체·재시작은 제외한다. 사용자는 앱을 직접 실행하고 실제 배포는 별도 요청으로 진행한다.
- 별도 상태 소유자·중복 제어 서버·새 UI 배치 체계는 만들지 않는다. 기존 core·인증·View 모델로 요구를 충족하며 구조적 한계가 입증되면 승인된 구조를 재검토한다. 근거: engineering 원칙 1, 2, 5, 7, 8 및 design 원칙 5, 8, 11.

## Behaviors

| # | 사용자가 관찰하는 행동 | 결정 |
| --- | --- | --- |
| B1 | `hide workspace info`로 자기 device·Workspace·checkout 및 현재 지원 기능을 조회하며 연결·소속을 확인하지 못하면 빈 성공 결과 대신 원인을 받는다. | D-01, D-06, D-09, D-17 |
| B2 | `hide file open <path>`는 호출 머신의 cwd 기준 파일을 자기 Workspace의 기존 문서 종류별 View로 연다. 존재하지 않음·읽기 거절·checkout 밖 경로는 실패 이유를 반환한다. | D-03, D-06, D-09, D-11 |
| B3 | `hide diff open <path>`는 자기 Workspace의 실제 Git 변경 diff를 연다. 변경이 없거나 대상 변경이 사라졌으면 그 상태를 알려주고 다른 Workspace의 diff로 바꾸지 않는다. | D-03, D-06, D-09 |
| B4 | `hide browser open <url-or-path>`는 자기 Workspace의 Browser View에 주소를 반영하며 잘못된 주소·허용되지 않은 scheme·읽을 수 없는 HTML을 명시적으로 거절한다. | D-02, D-06, D-08, D-12 |
| B5 | `hide view list`는 자기 Workspace의 area·View 식별자, 종류·대상·선택 상태를 반환하며 열린 View가 없으면 정상적인 빈 목록을 반환한다. | D-06, D-09 |
| B6 | `hide view select`는 지정한 View를 해당 area에서 선택하고 기본 키보드 입력 대상은 바꾸지 않는다. 사라진 대상은 재조회할 수 있는 오류로 반환한다. | D-06, D-07 |
| B7 | `hide view split`은 기존 View 분할 규칙으로 지정 display를 이동하고 `hide view move`는 자기 Workspace 안에서 area·순서를 바꾼다. 무효 분할·잘못된 목적지·기존 배치 상한 초과는 원래 배치를 보존하고 거절한다. | D-03, D-06, D-09, D-04 |
| B8 | `hide view close`는 요청한 View만 닫고 기존 규칙대로 빈 area를 정리한다. 이미 닫힌 View는 추가 변경 없이 그 상태를 반환한다. | D-06, D-13 |
| B9 | 마지막 View를 닫아 미저장 문서를 잃는 경우 닫기를 거절하고 View와 문서를 보존한다. 같은 문서를 유지하는 다른 View가 있으면 요청 View만 닫으며 저장·폐기·확인창을 대신 실행하지 않는다. | D-13 |
| B10 | 파일·diff 재열기 및 옆에 열기, 같은 URL의 browser 재열기는 기존 문서 재사용·배치·reload 규칙을 따른다. 새 열기로 기존 미저장 문서를 대체해 잃지 않는다. | D-02, D-03, D-06, D-13 |
| B11 | Workspace A의 CLI 작업 중 사용자가 B에서 입력하면 B의 화면·입력이 유지된다. 같은 Workspace 안에서도 기본 열기·선택·배치 작업이 키보드 포커스를 가져가지 않는다. | D-07 |
| B12 | `--reveal`을 명시한 요청만 호출자의 Workspace와 대상 View를 드러낸다. 다른 Workspace를 지정하는 우회 옵션은 없다. | D-07, D-09, D-06 |
| B13 | SSH 원격 pane에서 실행한 모든 지원 명령은 사용자 Mac의 그 원격 Workspace에 반영된다. 장치 간에 pane 또는 View의 짧은 ID가 같아도 대상을 혼동하지 않는다. | D-09, D-11 |
| B14 | 원격 `localhost:<port>` 페이지는 SSH를 통해 원격 서버에 연결되고 페이지의 일반 요청과 개발 서버의 WebSocket 갱신도 올바른 원격 서버를 사용한다. 실패를 현재 Mac의 같은 포트로 대체하지 않는다. | D-11, D-12, D-14 |
| B15 | 원격 HTML 미리보기는 같은 checkout 안의 상대 CSS·이미지·스크립트를 함께 제공한다. 경로 순회·심볼릭 링크로 root를 벗어난 리소스는 거절하고 원격 연결·기존 파일 접근 동의가 없으면 그 이유를 반환한다. | D-09, D-12, D-14 |
| B16 | Electron은 전체 기능을 제공하며 웹은 파일·diff·View 관리가 동작한다. 웹에서 Browser View는 기존 desktop-only 상태를 보이며 실제 페이지가 로드됐다고 보고하지 않는다. | D-08, D-15 |
| B17 | 변경 명령은 해당 요청의 core 반영 결과를 받아 성공·거절을 구분한다. browser open의 성공은 View 반영이며 반환값으로 device·Workspace·View와 요청을 식별할 수 있다. | D-04, D-15, D-06 |
| B18 | `hide view status`에서 브라우저의 로딩 전·로딩 중·완료·실패·연결 해제 상태를 구분한다. 아직 native 페이지가 생성되지 않은 비표시 View와 실제 로딩 완료를 동일하게 보고하지 않는다. | D-08, D-15, D-06 |
| B19 | browser `--wait`는 실제 페이지 완료 또는 실패를 기다리되 화면·포커스를 강제로 전환하지 않는다. 미지원 renderer·로딩 시작 불가·제한 시간 초과는 원인과 View의 현재 반영 상태를 반환하며 기다린 사실을 성공으로 표시하지 않는다. | D-07, D-08, D-15, D-06 |
| B20 | Hide 또는 해당 작업을 수행할 연결이 없으면 로컬·원격 모두 자동 실행 없이 앱 실행 후 다시 요청하라는 오류를 반환한다. daemon만 살아 있는 것을 사용 가능한 화면 연결로 오인하지 않는다. | D-16 |
| B21 | 로컬·원격의 새 Claude Code·Codex 세션은 실제 Hide 연결과 기능에 맞는 명령·제약 안내를 받는다. 일반 터미널 또는 Hide와 연결되지 않은 Herdr 세션에는 이 기능이 가능하다고 안내하지 않으며 CLI 도움말·기능 조회로 같은 계약을 확인할 수 있다. | D-11, D-17, D-18, D-06 |
| B22 | 호출 시점에 device·pane·Workspace 소속과 대상 View를 다시 확인한다. 다른 Workspace, 종료된 pane, 오래된 소속, 인증 실패 또는 사용할 수 없는 기능은 상태 변경 없이 거절하며 재조회·재연결 방법을 알린다. | D-03, D-09, D-17, D-04 |
| B23 | 각 요청은 한 번의 작업으로 반영된다. 동일 요청 재전송은 View·split·reload를 중복 생성하지 않으며 새 의도의 재열기와 구분한다. | D-04, D-10 |
| B24 | 대기 취소·시간 초과·전송 단절은 성공으로 숨기지 않는다. 이미 반영된 View는 보존하고 반영 여부가 미확정이면 요청 ID로 결과 또는 현재 상태를 확인할 수 있으며 무조건 새 작업을 재실행하지 않는다. | D-15, D-16, D-04, D-10 |
| B25 | 실패는 CLI의 비성공 종료·구조화된 원인·다음 행동으로 전달되고 실제 페이지 실패는 해당 Browser View의 기존 상태 표현을 사용한다. 사용자가 조치할 수 없는 내부 오류 때문에 새 전역 배너·선택창을 띄우지 않는다. | D-13, D-16, D-04, D-06 |

## Technical structure

- CLI → 인증된 hided 요청 → core의 device·pane·Workspace 검증 → 기존 문서·View 상태 → 웹·Electron 표시로 연결한다. 일반 UI 이벤트의 현재 화면 검사와 pane 요청의 소속 검사는 분리하며 shell이 상태 소유자가 되지 않는다.
- 기존 WebSocket 계약에 pane 범위의 호출 자격·기능 조회·요청 결과와 페이지 상태를 확장한다. 에이전트에 일반 shell의 전체 제어 토큰을 그대로 넘기거나 클라이언트가 보낸 ID만 믿지 않으며 자격은 소속·연결 수명에 묶는다.
- 원격 CLI의 반환 경로와 로컬 Browser에서 원격 서버로 향하는 경로를 기존 인증된 SSH 연결 체계 안에 둔다. 외부 인터페이스에 제어 포트를 공개하지 않으며 원격 HTML은 기존 device file host의 root·동의 경계로 읽고 Workspace별 origin으로 격리한다.
- 실제 로딩 상태는 Electron이 제공하고 core의 조회 가능한 상태로 전달한다. 표시되지 않은 View, native 페이지 존재, 페이지 로딩과 요청 반영을 구분하여 비표시 Workspace에서도 조회·대기 결과가 정확해야 한다.
- 컨텍스트 안내는 기존 런타임별 전달 형식을 확장한다. 원격 세션의 연결 bootstrap과 안내는 추가할 제품 경계이며 현재 구현되어 있다고 가정하지 않고, 원격 전역 설정 자동 설치 및 Memory 동기화로 범위를 넓히지 않는다.
- 신규 영속 DB·파일 동기화 서비스는 도입하지 않는다. 요청 I/O와 원격 자원 작업은 core lock 밖에서 수행하고 기존 snapshot·문서·View 저장 및 resource owner를 확장한다.

## Risks

- 호출 소속 위조·오래된 세션·장치 간 ID 충돌은 핵심 접근 위험이다. core의 실제 소속 검사와 연결 수명에 묶인 자격으로 제한하고 거절 결과를 검증한다.
- 원격 localhost의 WebSocket·재접속과 HTML 상대 리소스·origin 격리는 별도 연결 작업이다. 기존 CDP 역방향 bridge나 파일 byte 읽기만으로 완료를 주장하지 않는다.
- 현재 native 페이지는 표시된 View 위주로 생성되므로 비표시 페이지 대기는 상태 확장과 명시적인 실패 경계가 필요하다. 대기 편의를 위해 사용자 화면을 빼앗지 않는다.
- 기존 원격 hook 자동 설치 금지와 조건부 안내 요구를 함께 지켜야 한다. 별도 HOME·설정 fixture에서 두 런타임의 원격 세션 bootstrap을 검증하며 운영 hook 파일을 시험 대상으로 삼지 않는다.
- 동시 View 이동·닫기·재시도는 미저장 문서 손실과 중복 작업 위험이 있다. 문서 보존, 요청 결과 수렴, 실제 대상 재검증을 함께 확인한다.
- 인수는 별도 app·daemon·Herdr·SSH fixture에서 수행하고 운영 앱·pane·서버의 종료·초점 변경·설정 교체를 포함하지 않는다. native 표시는 식별한 후보 창의 실제 캡처로 확인하고 실행 근거는 로컬 run 경로에 둔다.
- 이후 구현 전달은 `main` 대상 PR과 필요한 CI 확인까지이며 자동 merge·운영 설치를 뜻하지 않는다. 현재는 PRD 작성만 수행하고 `human_approval: pending`을 유지한다.
- 인터뷰상 남은 제품 결정은 없다. 구현 착수에는 완성된 PRD에 대한 사용자 승인 또는 별도의 명시적 구현 요청이 필요하며, 배포에 필요한 새 자격·원격 설치 권한이 생기면 별도 범위로 다룬다.
