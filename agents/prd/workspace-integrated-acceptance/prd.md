# PRD: S9 Workspace UX 통합 수용과 전환 검토

## Goal

웹 셸로 옮겨 갈지 결정할 운영자가 S5.5~S8에서 따로 검증된 기능이 하나의 작업 여정으로 이어져 동작한다는 증거와, 이전 앱으로 돌아갈 수 있다는 증거를 한 번에 보게 한다.
각 단계는 자기 범위만 검증했으므로 Main에서 Workspace로 들어가 에이전트와 파일을 오가고, 나누고, 재시작하고, 원격 기기로 바꾸는 교차 흐름은 아직 누구도 확인하지 않았다.
S9는 새 기능을 만들지 않고 승인된 UX 계약 전체를 교차 흐름으로 확인하며, 발견한 결함을 고치고 실사용 전환 판단을 사용자에게 남긴다.

## Non-goals

- 새 기능, 새 화면, 새 단축키를 추가하지 않는다. 필요한 기능이 빠졌으면 결함으로 기록하고 해당 단계 계약을 기준으로 고치거나 후속으로 남긴다.
- Project Memory 웹 표면은 D-17에 따라 후속 TODO이므로 수용 대상이 아니다. 대신 macOS 앱의 Memory 표면·데이터·hook이 바뀌지 않았음을 확인한다.
- 실제 Browser 내장, pet, 전역 단축키 등 기존 미룸 항목은 계속 Electron 후속이며 수용 대상이 아니다(D-05).
- 실사용 전환, 설치 앱 교체, release, 운영 Herdr·pane 조작은 하지 않는다. 전환 결정은 사용자에게 남긴다.
- Swift 삭제(S10)는 시작하지 않는다. S10은 별도 삭제 PRD와 사용자 승인이 필요하다.
- 두 물리 기기가 필요한 검증은 두 기기를 쓸 수 있을 때만 수행하며, 불가하면 미실행으로 남기고 같은 기기 loopback 결과를 두 기기 증거로 쓰지 않는다.

## Behaviors

| # | 사용자가 관찰하는 행동 | 결정 |
| --- | --- | --- |
| B1 | 격리 fixture에서 Main → Project Overview → Workspace → 에이전트 pane → Explorer 파일 → Changes Diff → 다른 Workspace → 원래 Workspace로 이어지는 여정이 끊김 없이 동작하고, 각 전환이 에이전트나 pane을 새로 만들거나 종료하지 않는다. | D-01, D-04 |

| B3 | 세 아이콘으로 Agents/Together/Views를 오가도 탭·문서·pane이 닫히지 않고, Views 선택만으로 split이 생기지 않으며, 가장자리 접기 손잡이는 없다. Explorer와 Changes는 세 모드 모두에서 서로 독립적으로 열고 닫힌다. | D-06 |
| B4 | 단일클릭은 마지막 사용 View 영역의 preview 하나만 교체하고, 더블클릭·편집한 탭은 고정되어 교체되지 않는다. 이미 열린 파일은 기존 표시로 이동한다. 옆에 열기로 만든 두 표시는 한 편집 내용을 공유하고 스크롤은 각자이며, 표시 하나를 닫아도 내용이 남는다. | D-07 |
| B5 | 탭바 drag는 삽입선 뒤 재정렬·이동만 하고, 가장자리 drag는 하나의 목적 overlay 뒤 유효 drop에서만 split한다. Escape·무효 drop·공간 부족은 배치를 그대로 둔다. 반복 split과 경계 조절이 최소 크기를 지키고, 빈 split은 정리되며 마지막 Views는 모드를 바꾸지 않는 빈 상태로 남는다. | D-08 |

| B7 | 부모 pane의 모든 직접 자식 칩이 한 줄에 있고 넘치면 가로 스크롤한다. 칩으로 다른 탭의 기존 자식에 바로 가고 부모로 돌아오며, 관계 상세는 별도 메뉴에 있다. Views-only에서 에이전트를 열면 Together와 그 pane focus로, Agents-only에서 파일을 열면 Together와 그 문서 focus로 바뀌고, 상태 변화만으로는 화면이 바뀌지 않는다. | D-11 |

| B15 | 각 화면이 선택된 Pen 보드와 공용 library master, 토큰과 일치하고, 차이는 고쳐지거나 사람의 취향 검토 항목으로 기록된다. | D-13 |
| B16 | 발견한 결함은 고쳐져 회귀 테스트를 갖거나, 계약 변경이 필요하면 사람 검토 항목으로 남으며, 미실행·불가 검증은 PASS로 표시되지 않는다. 통과는 단위 테스트 재실행이 아니라 B1~B15의 실제 교차 흐름 관찰로 판단한다. 소스 수정이 없으면 PR 없이 수용 증거만 남는다. | D-12, D-14 |
| B17 | 결과 보고는 전환 판단에 필요한 사실(통과한 여정, 남은 결함, 미실행 검증, rollback 확인, 사람만 할 수 있는 판단)을 한곳에 모으고 실사용 전환 결정을 사용자 몫으로 남긴다. | D-15 |

## Technical structure

구조 변경은 없다.
S5.5~S8이 만든 core·hided·웹 경계와 소유자를 그대로 쓰고, 결함 수정은 해당 owner 안에서 한다.
통합 흐름은 기존 e2e 하네스(Herdr·hided fixture)와 격리 Herdr 서버, 명시적 상태 디렉터리에서 실행하고, 산출물은 agents/runs 아래에만 둔다.

## Risks

- S9 PRD는 S5.5~S8 merge 전에 작성되었다. 착수 시 merge된 소스와 각 단계의 실제 수용 결과를 대조한다.
- 교차 흐름에서 계약 수준의 결함이 나오면 S9 안에서 계약을 바꾸지 않고 사람 검토로 남기므로 전환 판단이 늦어질 수 있다.
- 두 물리 기기 검증과 시각 취향 판단은 사람이나 두 번째 기기가 있어야 한다. 실사용 전환 결정은 사용자에게 필요하며 착수 전 필요한 사용자 작업은 없다.
