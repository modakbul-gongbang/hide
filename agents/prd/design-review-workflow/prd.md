# PRD: 디자인 전달과 실제 화면 검증 흐름

## Goal

디자인 작업자는 선택한 디자인을 다른 머신의 구현자에게 온전히 전달하고, 구현한 화면이 기준과 어떻게 다른지 한 번의 검증 실행으로 확인할 수 있다.
리뷰어는 PR 안에서 디자인과 실제 화면, 자동 확인 결과와 자신의 판단이 필요한 부분을 바로 구분한다.
기존 승인과 리뷰 단계 안에 이 흐름을 통합하여 반복 문서 작업과 상태 재현 시간을 줄인다.

## Non-goals

- 전체 제품 화면을 새로 설계하지 않는다. 사이드바의 프로젝트, 체크아웃, 에이전트 행부터 적용하고 다른 화면은 해당 기능을 변경할 때 확장한다.
- Pen을 React 코드로 자동 변환하거나 모든 픽셀을 일치 판정하지 않는다. 폰트 렌더러 차이를 허용하되 승인된 배치 규칙과 실제 가독성을 확인한다.
- 설치된 앱, 운영 데이터, 원격 서비스, 인증 설정, 브랜치 보호를 변경하지 않는다. 이번 결과는 검토할 수 있는 두 PR이며 배포나 머지는 포함하지 않는다.
- 새로운 상시 서비스나 별도의 디자인 관리 제품을 만들지 않는다. 저장소의 토큰, 갤러리, 검사 스크립트와 PR 템플릿을 확장한다.

## Decisions

| D-n | 결정 | 근거 |
| --- | --- | --- |
| D-01 | 별도 worktree에서 한 담당자가 프로세스 개선을 구현한 다음 실제 예시 디자인 작업을 수행한다. | 사용자: "worktree에 작업 한 번 쭉 시켜서 우선 구현하고 그 작업하는 녀석한테 실제로 예시 디자인 작업 하나 줘서" |
| D-02 | 결과는 개선 PR 하나와 개선 후의 리뷰 형태를 보여주는 임시 Draft PR 하나다. 둘 다 머지하지 않는다. | 사용자: "내가 보는 결과물은 PR2개이고 하나는 이 작업에 대한 PR 나머지 하나는 바뀌고 나서 보일 형태의 PR" |
| D-03 | 선택한 Pen과 그 라이브러리 및 필요한 자산의 버전, PNG, 핵심 배치 규칙을 휴대 가능한 로컬 묶음으로 보존한다. 승인 기록이 없으면 제안 또는 위임된 가정으로 표시한다. | 가정: 원격 작업에서 승인 당시 기준이 사라지는 실패를 막는다. 사용자가 이번 구현과 예시 선택을 일괄 위임했다. |
| D-04 | 기존 갤러리에 실제 프로젝트, 체크아웃, 에이전트 행을 재사용하여 대표 상태를 표시한다. | 가정: 기본 부품뿐 아니라 배치 차이가 발생한 실제 제품 조합을 확인한다. engineering 7의 기존 구조 활용. |
| D-05 | 기존 정적 검사에 필요한 실제 브라우저 배치 검사를 연결하고, 변경 대상의 비교 자료를 한 실행 경로로 준비한다. | 앞선 제안의 핵심 세 가지를 이번에 작업하도록 위임했다. 별도 승인 단계를 늘리지 않는다. |
| D-06 | 자동 검사는 승인 또는 명시된 제안 규칙을 기준으로 들여쓰기, hover 높이 안정성, 제목과 시간 및 조작부 겹침을 확인한다. | 사용자: "들여쓰기나 그런거 왜 달라?" 및 "마우스오버했을 때 ... 높이가 바껴". engineering 12의 외부 기대값. |
| D-07 | 비교 결과는 기준 디자인, 현재 정식 Pen, 실제 화면의 구분과 입력 조건을 유지하고 사람의 시각 판단을 자동 PASS로 대체하지 않는다. | 가정: 코드와 Pen을 함께 잘못 수정해도 최초 기준과 차이를 볼 수 있어야 한다. |
| D-08 | 예시 PR은 첫 PR을 base로 쌓으며 사이드바 자식 행의 들여쓰기와 긴 제목 배치를 다듬는 작은 디자인 변경으로 한다. 12px 들여쓰기는 위임된 제안이며 사용자 승인으로 꾸미지 않는다. | 가정: 사용자가 문제 삼은 사례로 새 흐름을 실제 사용하는 것이 가장 직접적인 설명이다. 취향은 임시 PR에서 검토한다. |
| D-09 | 비교 PNG는 저장소에 커밋하지 않고 기존 PR 이미지 첨부 또는 설정된 자산 저장소를 통해 리뷰어가 볼 수 있게 게시한다. | 사용자는 실제 PR에서 보일 형태를 요청했다. 저장소의 Evidence 경계와 기존 ship 경로를 따른다. |
| D-10 | Pen 사용 가능 여부, 입력 누락, 다른 소스 버전, 캡처 실패를 명시적으로 보고하며 필요한 시각 검증이 빠진 실행을 완료로 표시하지 않는다. | 가정: mini에 Pen이 없었던 경우 정적 검사가 시각 검증처럼 보인 문제를 방지한다. |

## Behaviors

| # | 사용자가 관찰하는 행동 | 결정 |
| --- | --- | --- |
| B1 | 디자인 작업자는 선택한 디자인의 기준 묶음을 생성하고 다른 checkout에서도 원래 라이브러리와 자산을 포함한 같은 기준을 열 수 있다. 원래 묶음은 재실행으로 덮어쓰지 않는다. | D-03 |
| B2 | 기준 묶음은 선택 시점과 입력 버전, PNG, 폭과 테마 및 콘텐츠 조건, 중요한 배치 규칙을 식별하며 사용자 승인과 위임된 제안을 구분한다. 기존 PRD의 결정 기록을 중복 관리하게 하지 않는다. | D-03, D-07 |
| B3 | 실제 앱에서 사용하는 세 종류의 행을 개발용 갤러리에서 기본, 선택, hover/focus, 접힘과 펼침, 부모와 자식 상태로 확인한다. 보여주는 상태는 실제 제품이 표현하는 상태다. | D-04 |
| B4 | 갤러리는 긴 한글 제목, 메타데이터 유무, 좁은 사이드바와 큰 글자 조건에서 잘림과 배치를 확인할 수 있고 Light와 Dark를 지원한다. 생산 빌드에 개발용 갤러리는 포함되지 않는다. | D-04 |
| B5 | 작업자는 문서에 적힌 한 검증 실행 경로로 기존 정적 검사, 대상 배치 검사, 비교 자료 생성을 실행하며 각 단계의 실제 결과와 실패 원인을 확인한다. | D-05, D-10 |
| B6 | 들여쓰기 기대값 위반, hover 전후 행 높이 변화, 제목과 시간 및 조작부의 겹침을 실제 브라우저에서 탐지한다. 테스트 기대값을 현재 구현에서 역으로 복제하지 않는다. | D-06 |
| B7 | 비교 자료는 같은 콘텐츠와 폭 및 테마 조건의 기준 디자인, 현재 Pen, 실제 화면을 구분해서 보여준다. 주요 상태와 두 테마를 검토할 수 있고 자동 검사 결과와 사람에게 남은 판단을 따로 표시한다. | D-07 |
| B8 | Pen 또는 로그인 부재, 파일 누락, stale 입력 및 캡처 실패는 성공 결과로 처리되지 않는다. 실행 결과는 원인과 다시 실행할 방법을 알려주고 기존 기준을 보존한다. | D-10 |
| B9 | 원격 구현자는 기준 묶음만으로 숫자와 이미지를 확인하며, Pen 렌더링이 필요한 검증은 가능한 머신에서 이어 수행할 수 있다. 렌더링 전에는 시각 검증이 미완료임이 유지된다. | D-03, D-10 |
| B10 | PR용 결과에는 나란히 비교하는 이미지와 대표 상호작용 상태, 확인한 조건, 미확인 범위, 사람의 판단 항목이 담긴다. 로컬 경로나 숨겨진 artifact만을 근거 링크로 제시하지 않는다. | D-07, D-09 |
| B11 | 명령은 변경 대상만 지정할 수 있으며 매번 모든 화면과 상태 조합을 검사하도록 요구하지 않는다. 기존 승인 및 리뷰 안에서 동작하고 별도 확인 문서를 반복 작성하게 하지 않는다. | D-05 |
| B12 | 종료, 취소 및 오류 후 해당 실행이 시작한 임시 프로세스와 브라우저 연결을 정리하고 이미 열려 있던 앱, pane 및 서비스를 보존한다. | D-05, D-10 |

## Technical structure

기존 저장소 안의 토큰 생성, 디자인 파일, 개발용 갤러리, 브라우저 검증 및 PR 증거 게시 경로를 확장한다.
기준 디자인과 실행 증거는 무시되는 작업 디렉터리에 두고 소스 및 정식 디자인 변경만 커밋한다.
공개 API, 운영 데이터 저장 구조, 인증 경계 및 상시 프로세스 구조는 변경하지 않는다.

## Risks

- Pen과 브라우저의 폰트 및 레이아웃 엔진이 다르므로 배치 규칙 위반과 렌더러 차이를 구분한다. 전체 픽셀 일치를 요구하지 않는다.
- 공유 컴포넌트를 갤러리에 노출하면서 실제 앱의 상호작용이 바뀌지 않도록 실제 행과 앱 맥락에서 확인한다.
- 예시 디자인은 위임된 가정이다. PR에서 사용자가 결과를 판단할 때까지 승인 완료나 채택 완료로 표현하지 않는다.
- 게시할 이미지는 합성 예시 데이터와 제품 영역만 담고 홈 경로, 머신명, 인증 정보가 포함되지 않는지 확인한다.
- 사용자에게 필요한 추가 자격 증명이나 운영 조치는 현재 없다. 실제 도구 실패가 발생하면 검증 미완료로 명확히 기록한다.
